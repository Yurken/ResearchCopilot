# 小妍持续进化规划

> 文档性质：长期维护的产品、评测与工程总纲
>
> 当前版本：`0.2.1`
>
> 建立日期：2026-07-29
>
> 最近更新：2026-08-06
>
> 当前阶段：阶段 A「建立可信基线」
>
> 当前唯一主线：让用户跨天续接研究任务时少重复解释、能直接进入下一步
>
> 下次强制更新：Codex 开发模型候选变更、核心 Agent 架构变化或小妍正式版本发布前
>
> 适用范围：以 Desktop 为旗舰端，选择性同步 Web / Mobile

## 1. 一页执行摘要

小妍“越用越好用”不是功能越来越多，而是同一用户持续使用后，完成科研任务所需的重复解释、人工纠正和失败恢复成本持续下降。

当前阶段只验证一个核心结果：

> 用户间隔数天回到一个研究主题，能够从可信 checkpoint 直接恢复目标、证据、未决问题和下一步，并在一次会话内产生可用结果或研究资产。

本阶段的决策边界：

| 项目 | 当前决定 |
| --- | --- |
| 北极星指标 | 有效续接率 |
| 每轮工作上限 | 1 个主假设、1 个端到端切片、最多 2 个辅助工程项 |
| 每次 Codex 候选必跑 | E01 续接、E02 证据问答、E06 路由、E08 隐私 |
| 当前首要缺口 | 没有可执行评测集、跨版本基线和持久化模型指纹 |
| 当前不做 | 黑盒自动改代码、无授权主动执行、为了追新模型而大范围重写 |
| 采用升级的条件 | 核心质量不退化，目标切片有可复现收益，并有对应代码与测试落地 |

最近两个迭代的推进顺序：

1. `已完成` checkpoint 从工作台显式交接到小妍，恢复原会话并预填可编辑续接请求；
2. `下一步` 建立 E01、E02、E06、E08 的固定夹具、评分表和首版人工基线；
3. 持久化 Agent 运行的模型指纹、策略版本、耗时和失败分类；
4. 将设置页反馈改为结构化类别，并可选关联会话/请求。

## 2. 目标、边界与原则

### 2.1 用户可感知目标

- 小妍越来越理解用户的研究主题、目标、稳定偏好与约束；
- 上次做到哪里、为什么这样决定、下一步做什么，都能自然续接；
- 用户明确纠正过的问题不在错误作用域内重复发生；
- 重要结论有来源，未知和冲突信息会被明确标记；
- 任务失败后能保留进度、解释原因并从合理位置恢复。

### 2.2 不属于本规划的目标

- 不以对话次数、功能入口、回答长度或 Token 消耗证明“更好用”；
- 不追求保存所有历史；
- 不让运行中的小妍自行修改生产代码；
- 不把模型能力等同于产品能力；
- 不要求 Web / Mobile 与 Desktop 同步实现全部能力。

### 2.3 长期原则

1. **连续性优先**：先减少重复输入和上下文断裂，再增加功能数量。
2. **最小充分上下文**：只向任务提供必要、来源明确且仍然有效的信息。
3. **证据优先**：科研结论尽量关联论文、知识、实验或投稿资产；无法确认时说明不确定性。
4. **记忆可控**：记忆可查看、可纠正、可删除、可关闭，并有清晰作用域。
5. **自动化可撤销**：主动建议可忽略，高影响动作必须确认。
6. **评测先于升级**：新模型先成为候选，通过门槛后才能成为默认开发能力。
7. **结构边界不退让**：继续遵守 [`development-principles.md`](./development-principles.md)，页面只组合，状态、副作用与远程调用进入 feature、hook 或 service。

## 4. 北极星指标与护栏

### 4.1 北极星指标：有效续接率

定义：用户主动从 checkpoint、工作台或研究主题续接后，在一次任务内满足以下全部条件的比例：

1. 没有重新输入已保存的目标和关键背景；
2. 小妍引用了正确的研究主题或资产；
3. 用户接受一个下一步，或产生被保存/采用的结果资产；
4. 没有因错误上下文重开会话或清空重来。

计算口径：

```text
有效续接率 = 有效续接任务数 / 用户主动发起的续接任务数
```

在自动事件尚未实现前，使用去标识化人工任务记录建立基线，不用点击次数伪装质量结论。

### 4.2 结果指标

| 指标 | 解释 | 首阶段证据 |
| --- | --- | --- |
| 有效续接率 | 用户能否真正接着做，而非只看到 checkpoint | E01 人工评分 + 续接任务结果 |
| 任务一次完成率 | 无需重试或大幅改写即可采用 | 任务结果评价 |
| 证据覆盖率 | 应有来源的结论中具有可打开证据的比例 | E02、E03、E05 |
| 失败恢复率 | 失败后保留部分结果并成功续跑的比例 | E07 |
| 有效记忆率 | 被召回记忆中被用户确认有帮助的比例 | E09 |

### 4.3 不可退化护栏

- E08 隐私与安全不得出现任何严重问题；
- 事实或引用错误不得增加；
- 为获得相同质量，不得无解释地显著增加成本或 P95 延迟；
- 用户关闭长期记忆后，不得继续产生隐式长期个性化；
- 自动化增加时，撤销、关闭和失败恢复路径必须同步存在；
- 评测或可观测数据不得复制保存整段研究正文。

## 5. 每轮迭代的运行机制

每轮只能有一个主假设。没有明确主假设、证据和杀停标准，不进入开发。

### 5.1 假设卡

```markdown
- 用户问题：
- 主假设：如果我们……，那么……，因为……
- 目标用户与场景：
- 当前基线：
- 目标变化：
- 最便宜验证：
- 杀停标准：
- 对应评测：
- 端到端切片：
- 代码边界：
- 隐私影响：
- 回滚方式：
```

### 5.2 标准闭环

```text
反馈或失败样例
  → 去标识化并归类
  → 写假设卡与杀停标准
  → 冻结代码、数据、配置和模型基线
  → 只改一个主要变量
  → 自动测试 + 固定评测 + 人工科研任务
  → 采用 / 继续试验 / 回退 / 放弃
  → 更新本文、评测集与迭代记录
```

### 5.3 完成定义

一次持续进化迭代只有同时满足以下条件才算完成：

- 主假设有前后对比证据；
- 目标切片从入口到资产或结果完整可用；
- 受影响评测已运行，失败样例未被删除或弱化；
- 代码、测试和文档一致；
- 隐私、性能和恢复护栏通过；
- 记录采用、回退或放弃的明确结论；
- 下一轮只保留一个最高价值假设。

## 6. Codex 升级状态机

### 6.1 状态定义

```text
发现候选
  → 登记指纹
  → 冻结旧基线
  → 核心门禁评测
  → 受影响评测
  → 采纳 / 拒绝 / 继续观察
  → 代码适配与测试
  → 灰度与复盘
```

- **候选**：新模型或关键代理能力可用，但尚未改变仓库默认工作方式；
- **采纳**：评测证明收益，且已通过代码、测试和文档将收益落到小妍；
- **拒绝**：未达门槛，保留旧流程并记录失败样例；
- **继续观察**：证据不足，不宣称升级完成。

“每次 Codex 升级都迭代文档和代码”指每次被正式采纳的升级。所有候选都必须留下评测和文档记录；没有代码收益的候选不得为了形式制造空改动。

### 6.2 模型指纹

每轮至少记录：

- 可见模型名、版本或“构建号未知”；
- 运行日期、宿主与推理配置；
- 可用工具、技能、插件与上下文限制；
- 仓库 commit、工作区是否干净；
- 评测数据版本、Prompt 版本、工具契约版本；
- 对照模型或最近可信基线。

### 6.3 升级步骤

1. 在相同代码、配置、数据和评测规则上冻结旧基线；
2. 新候选运行核心门禁 E01、E02、E06、E08；
3. 根据本轮能力和代码切片运行受影响场景；
4. 将每项标注为 `提升 / 持平 / 退化 / 未知` 并附证据；
5. 只选择一个能利用新能力的端到端切片；
6. 落地对应 Prompt、Context、Tool、Runtime、UI 或 Data 改进；
7. 运行相关测试、type-check、lint 和人工验收；
8. 通过门槛后灰度，失败则回退并把样例加入评测集；
9. 更新本文版本、当前状态、优先级和迭代记录。

### 6.4 能力到代码的映射

| 新能力 | 优先检查的产品落点 | 不应直接做的事 |
| --- | --- | --- |
| 更可靠的工具调用 | 类型化工具契约、参数校验、错误恢复、幂等 | 直接扩大高风险工具权限 |
| 更长上下文 | 上下文选择、预算、来源和冲突检测 | 默认把全部历史塞入 Prompt |
| 更强视觉 | 图表/截图理解、来源追溯、隐私遮盖 | 默认保存或上传截图正文 |
| 更强规划/并行 | Agent 路由、执行波次、局部重试 | 无上限增加 Agent 和步骤 |
| 更低延迟/成本 | 任务分层路由、快速预览、后台处理 | 在质量未验证时只追求便宜 |
| 更强编码能力 | 拆分遗留大文件、补测试和契约 | 借机无基线地重写整个模块 |

## 7. 分层评测体系

### 7.1 评测层级

| 层级 | 何时运行 | 范围 | 目的 |
| --- | --- | --- | --- |
| 核心门禁 | 每个 Codex 候选、每次核心 Agent 改动 | E01、E02、E06、E08 | 防止连续性、证据、路由和隐私退化 |
| 受影响集 | 每个功能迭代 | 与改动直接相关的场景 | 证明目标切片收益 |
| 完整集 | 正式版本发布前 | E01—E10 | 检查跨模块回归 |

### 7.2 场景目录

| 编号 | 场景 | 主要验证 |
| --- | --- | --- |
| E01 | 间隔多日后续接研究主题 | checkpoint 召回、目标一致性、下一步可执行性 |
| E02 | 基于本地论文回答事实问题 | 检索质量、引用准确性、不编造 |
| E03 | 精读论文并提取方法与局限 | 结构遵循、证据定位、未知项处理 |
| E04 | 从论文生成复现实验计划 | 依赖完整性、风险识别、实验资产关联 |
| E05 | 根据证据辅助写作或改稿 | 论证边界、引用保持、文风约束 |
| E06 | 多意图任务的 Agent 与工具选择 | 路由准确性、最少充分工具、执行顺序 |
| E07 | 模型、网络或工具中途失败 | 部分结果保留、错误说明、重试与续跑 |
| E08 | 敏感文本、截图或受限应用输入 | 阻断、遮盖、确认、无意外持久化 |
| E09 | 用户纠正事实或偏好后再次请求 | 纠正生效、作用域正确、可撤销 |
| E10 | 桌面助手解读并导入资产 | 来源追溯、模型路由、导入和清理 |

### 7.3 场景文件必须包含

```yaml
id: E01-continue-research-normal
version: 1
fixture_type: synthetic
preconditions: []
user_input: ""
expected_context: []
forbidden_context: []
expected_tools: []
forbidden_tools: []
expected_evidence: []
assertions: []
privacy_assertions: []
scoring_notes: ""
```

真实研究材料不得直接进入仓库。优先使用合成夹具；必须使用真实失败样例时，先去标识化并记录授权和处理方式。

### 7.4 评分与硬失败

每个场景按 0—4 分：

- `0`：未完成，或出现严重事实、权限、隐私问题；
- `1`：有输出但无法用于真实任务；
- `2`：基本可用，需要明显人工纠正；
- `3`：可直接使用，仅需轻微调整；
- `4`：质量高，证据、交互和恢复路径均清晰。

以下任一情况直接判定不通过，不用平均分掩盖：

- 未授权外发或持久化敏感内容；
- 编造关键论文、实验数据或来源；
- 高影响动作绕过确认；
- 失败后破坏、覆盖或丢失用户资产；
- E01、E02、E06、E08 中任何一项下降超过 1 分且无缓解措施。

### 7.5 采纳门槛

- 核心门禁无硬失败且平均分不下降；
- 目标切片相对旧基线有可复现改善；
- 若质量持平，只有成本或延迟有明显、稳定收益时才采纳；
- 自动测试覆盖新增契约和已发现失败样例；
- 无法通过时保留旧流程，结论记为“拒绝”或“继续观察”。

评测报告较长时放入 `docs/evolution-runs/YYYY-MM-DD-<model-fingerprint>.md`；本文只保留决策摘要和链接。

## 8. 关键杀停假设

以下是当前最可能让规划失效的承重假设，按“影响 × 可能错误 × 测试便宜程度”排序。

### K1：研究续接是当前最值得优先解决的问题

- **为什么可能成立**：小妍已有大量科研资产和 checkpoint，连续使用价值取决于能否重新进入状态。
- **失败条件**：目标用户更在意单次任务质量，续接入口很少被使用或没有减少重复说明。
- **本周证据**：用 5 个去标识化研究任务，让用户分别从空白会话和 checkpoint 续接，记录重复输入和完成时间。
- **杀停标准**：多数任务没有减少重复输入，或用户不愿主动使用续接入口。
- **最便宜测试**：先做 5 组配对人工测试，不先建设完整埋点。

### K2：脱敏行为信号足以衡量“更好用”

- **为什么可能成立**：保存、导入、继续、重试和撤销能反映部分真实结果，且不需要上传正文。
- **失败条件**：行为信号与人工质量判断经常相反，例如复制了错误答案或因 UI 摩擦没有保存好答案。
- **本周证据**：对 20 次合成/内部任务同时记录行为信号与人工 0—4 分。
- **杀停标准**：两者一致率低于 70%，或无法区分“结果差”与“交互差”。
- **最便宜测试**：先用本地表格对照，不先建设远程分析系统。

### K3：固定评测能预测真实科研任务

- **为什么可能成立**：E01—E10 覆盖了小妍的关键工作流和主要安全边界。
- **失败条件**：真实高频问题在评测中没有对应样例，或评测提升但真实任务质量不变。
- **本周证据**：将最近可用的去标识化反馈逐条映射到 E01—E10，并标记无法覆盖项。
- **杀停标准**：超过 20% 的高频失败无法映射，或连续两轮真实失败未被评测捕获。
- **最便宜测试**：做一次反馈—场景映射审查，而不是立即扩充大量用例。

### K4：Codex 升级能通过代码适配转化为产品收益

- **为什么可能成立**：更强工具、视觉、规划和编码能力可以改善上下文、契约、恢复和测试质量。
- **失败条件**：收益只存在于演示输出，落地后核心门禁不升反降，或维护成本超过收益。
- **本周证据**：每次只选一个垂直切片，在同一夹具上做旧/新对照。
- **杀停标准**：目标切片无可复现改善，或引入核心门禁退化。
- **最便宜测试**：先改一个 Prompt/Context/Tool 契约并回归，不做跨模块重写。

## 9. 技术演进主线

### 9.1 评测与运行记录

下一完成定义：

- 核心门禁夹具可版本化、可重复运行；
- Agent 运行持久化模型指纹、路由策略、Prompt/工具契约版本、耗时和失败类型；
- 评测报告能关联 commit、配置和数据版本；
- 不保存不必要的原始研究正文。

### 9.2 研究上下文

下一完成定义：

- 每段上下文带来源类型、资产 ID、更新时间和选择原因；
- 有明确上下文预算、去重、冲突和过期策略；
- E01、E02 可断言应选与不应选的上下文；
- 策略位于 service，不散落在页面和 Prompt 字符串中。

### 9.3 记忆与偏好

下一完成定义：

- 区分事实、偏好、决策、开放问题和下一步；
- 候选记忆具有作用域、来源、置信度和过期时间；
- 用户能查看、纠正、删除和关闭；
- E09 能证明纠正生效且不污染其他主题。

### 9.4 Agent 与工具

下一完成定义：

- 工具有结构化输入输出、错误类型和风险等级；
- 路由结果可解释并可降级；
- 状态机支持停止、局部重试和幂等；
- E06、E07 记录无效调用、恢复位置和最终结果。

### 9.5 反馈与主动协作

下一完成定义：

- 反馈可选择连续性、事实、证据、工具、交互、性能或隐私类别；
- 用户可选择关联会话/请求，并在提交前预览数据；
- 主动建议说明触发原因，可忽略、稍后和关闭同类建议；
- 没有可靠评测前，不扩大自动执行权限。

## 10. 路线图

### 阶段 A：建立可信基线（当前）

退出条件：

- E01、E02、E06、E08 有版本化夹具、评分规则和首版报告；
- Agent 运行记录包含可比较的模型与策略元数据；
- 第一次“研究续接”前后对比完成；
- 结构化反馈可以把失败回流到评测场景。

### 阶段 B：让研究真正可续接

退出条件：

- 有效续接率有稳定基线并连续两个迭代改善；
- 上下文来源与选择原因可检查；
- 失败任务能从合理节点恢复；
- E01、E07 稳定达到可用水平。

### 阶段 C：形成可控个性化

退出条件：

- 有效记忆率高于误召回率；
- 错误记忆可快速纠正且作用域正确；
- 关闭记忆后不再产生隐式长期个性化；
- E09 稳定达到可用水平。

### 阶段 D：适度主动与跨模块闭环

退出条件：

- 建议能进入“执行 → 资产 → checkpoint → 下次续接”闭环；
- 主动建议采纳率提升且忽略/关闭成本不增加；
- 核心科研结论有来源或明确不确定性；
- Codex 候选评测和灰度流程成为常规发布门禁。

## 11. 数据与隐私边界

必须区分两类数据：

- **用户主动创建的产品资产**：聊天、笔记、论文、实验、checkpoint 等，可按功能设计保存在本地；长期记忆受用户开关、详情保护和删除能力约束。
- **用于改进的可观测数据**：只记录完成状态、耗时、错误类型、路由、工具和用户显式反馈等最小字段，不重复保存整段正文。

规则：

- 默认不上传论文正文、聊天正文、截图内容、API Key、绝对路径或未公开研究材料；
- 反馈中的文字、截图和日志仅在用户明确选择并确认后上传；
- 真实案例进入评测前必须去标识化，无法可靠脱敏时使用合成案例；
- 每个新增事件必须写明用途、字段、存储位置、保留期、开关和删除路径；
- 本地优先不等于无需告知，任何持久化都应在产品说明中可理解。

## 13. 维护规则

- 文档版本使用语义化规则：愿景或机制变化升 `MAJOR`，阶段、指标或评测变化升 `MINOR`，状态和记录变化升 `PATCH`；
- 每次 Codex 候选变更、核心 Agent 架构变化和正式版本发布前必须更新；
- 完成事项移入迭代记录，不直接删除历史结论；
- 连续两个迭代没有证据支持的事项降级、重写或移除；
- 单功能细节进入独立 PRD，本文只保留跨模块决策和验收；
- 规划与实现不一致时，以代码和测试为事实基线，并在同一轮修正文档；
- 任一时刻只保留一个“下一轮唯一主假设”。
